# Review: the process rides in the repo — monitor from the tree, guard pinned to origin/main

Three independent fresh-context rounds, each a subagent that had not seen the
reasoning behind the change. Round one (on the naive draft, all hooks from the
working tree) returned REQUEST CHANGES: the guard would have run from the very
tree it guards, and eleven hand-transcribed hook entries had no check keeping
them equal to the manifests. Round two (on the pinned-guard redesign) returned
REQUEST CHANGES again: drift between the enforcing origin/main copy and the
tree copy was invisible, the guard side of the parity check was a substring
match, async on a guard entry was unchecked, every pull_request CI run would
have gone red, and the fail-open message misdiagnosed a missing interpreter as
an unextractable ref. Round three verified each demanded fix empirically and
returned APPROVE.

## What was verified, empirically, in round three

1. CI pull_request checkouts fetch refs/heads/main into refs/remotes/origin/main
   before `uv run forge check`, so the drift rule cannot redden a PR for a
   reason unrelated to the PR.
2. The pinned Stop runner: exit 2 with the blocking message on a dirty
   protected tree; exit 0 with a "not extractable" systemMessage in a non-git
   directory; exit 0 with a "no python interpreter found" systemMessage on a
   Python-less PATH; a loud mktemp-failure path.
3. A pinned guard runner registered on an event the guard manifest does not
   declare is flagged (ghost-entry direction of the drift rule).
4. Malformed manifests produce error strings, never exceptions.
5. Monitor entries are compared on args, timeout, async, command and type.
6. `uv run forge check` fails on exactly one item — the designed-red drift rule,
   because this tree is ahead of origin/main until pushed — and all 21 proofs
   under "the checks themselves" pass, including the eleven parity proofs.

Verdict: APPROVE.
